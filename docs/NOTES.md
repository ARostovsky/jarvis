# Notes folder

A workspace can point at a persistent markdown folder, the notes folder, that outlives the workspace and can be shared by workspaces on the same project. Jarvis (the arbiter) reads it at the start of a goal, keeps it up to date and commits it to git. The Open items panel shows one file of it.

This page is the reference for the notes folder: use, layout, open items, commits, archiving, configuration, endpoints and internals. [USAGE.md](USAGE.md) and [ARCHITECTURE.md](ARCHITECTURE.md) only point here.

## Setting it up

Set the folder in the **+** (New workspace) dialog, or later in the tab's right-click menu (`Notes folder…`, empty clears it). The server creates a missing folder and refuses your home folder and any folder above it (every agent would get write access to all of home), and a workspace whose notes folder is its project folder.

`WorkspaceMeta.notes` (an absolute path, kept in `workspaces.json` and `meta.json` like `project`) holds it. `agentOptions()` runs when a session starts, so a change applies when a session next starts or resumes (after a restart or `stop`, then a message). There is no live reload.

**Project and notes pairing.** The dialog remembers the pair. `GET /recent` lists the project and notes folders used before (newest first, existing ones only), and `projectNotes`, the notes folder of the newest live or archived workspace per project (by folder mtime). When you pick or type a project, the notes field is prefilled from it, with the hint `from previous workspace`, if the field is empty or still holds that earlier prefill. A value you typed is never overwritten; a project without history clears a prefill the dialog made itself. With `?project=` the server normalizes the typed path (resolved, symlinks followed) and answers `projectNote` (`''` for no history); the dialog asks on each edit of the project field. A pair whose notes folder is the project folder is left out. The list is read when the dialog opens and is seeded once from existing workspaces. It is stored in `recent.json` in the data dir.

A workspace started by `create_workspace` gets the same project and notes folder (unless another project is given); see [USAGE.md](USAGE.md).

## Layout

```
<notes>/
  README.md CLAUDE.md decisions.md ...   project-wide, shared
  status.md, open-items.md, journal/     legacy files of the shared layout: left as they are, arbiters do not add to them
  workspaces/
    index.md                             generated by the server, never edited by arbiters
    _archive/<workspace-id>/             archived workspaces
    <workspace-id>/
      status.md                          current state; the first `Summary:` line is the index entry
      open-items.md                      strict item lines, see Open items
      journal/YYYY-MM-DD.md              running log
```

- Each workspace has its own folder, named by the workspace id, which never changes, so a rename moves nothing. Only that workspace's Jarvis writes it; other workspaces read it.
- `ensureWorkspaceNotes()` creates the folder, `journal/` and the two templates with `O_EXCL|O_NOFOLLOW`: it never overwrites or follows anything and refuses a symlinked `workspaces/` or `<id>/` (the id must match `[a-z0-9-]+`). It runs in `addWorkspace()` (also for `create_workspace`), in `setWorkspaceNotes()` (which creates the folder before it sets `meta.notes`, so a refused folder never stays in memory) and, for workspaces from before this layout, in `ensureOwnNotes()` when the arbiter's session starts. `addWorkspace()` keeps the id suffix off every existing `workspaces/<id>/` name. Templates hold no secrets. Created files are claimed for the workspace, so its next commit carries them.
- `workspaces/index.md` is generated by `writeIndex()` at workspace creation, at arbiter session start and before each `commitNotes()` of an arbiter turn. One line per real (non-symlink) folder: `- [<name or id>](<id>/status.md): <Summary> (open: N, you: M)`, from the `Summary:` line of `status.md` (`-` for a missing or template one) and the open items (open and parked count as open). Files are read without following symlinks (size capped); the index is written to a temp file and renamed; a failure only logs. It is claimed for the workspace whose turn wrote it. Do not edit it.
- **Workspaces from before this layout** get their folder at the next start of their Jarvis session, and one `[notes layout changed]` message in front of its next message asking it to copy its own entries from the shared `status.md` and `open-items.md`. The marker `notes-layout-told` in the workspace's data dir is written after the notice was delivered, so a restart in between tells it again (`addWorkspace()` and `setWorkspaceNotes()` write it at once). The shared files and the old `journal/` stay as they are.
- **Legacy journals** (`<notes>/journal/<date>-<journal key>.md`, the key being the slug of the workspace's name, at most 40 characters, plus the unique suffix of its id, `journalKey()` in `src/slug.ts`) are no longer added to. Only for them the rename machinery remains: `syncJournals()` moves them to the current key at rename time and in each `commitNotes()`, merging first into a `.merge-<date>-<key>-<random>` file so a line appended meanwhile is never lost (a leftover of a crash is merged at the next sync and never attributed or committed). `newLines()` merges a stale rewrite, `openPlain()` refuses symlinks, hard links and FIFOs, and `journalOwner()` decides whose a file is. A rename sends the arbiter a one-time note (`noteJournalMoved()`), only when such a file actually moved. Apart from this move and the restore move below, the server never moves, rewrites or deletes notes.
- Size rules: files read on every spawn or arbiter start must not grow. `NOTES_SIZE_CAPS` (`CLAUDE.md` 6 KB, `README.md` and `access.md` 10 KB) drives `notesSizeWarnings()`, which `arbiterNotesPrompt()` logs and appends as a one-line note. It only warns, never edits.

## What agents do with it

`agentOptions()` passes the folder as `additionalDirectories` to every agent and appends a prompt:

- Jarvis is told to read it at the start of a goal and to maintain it. Every other agent is only told to read it, and to edit it only when its task asks for it, by absolute path (also in Bash) and without running git there, because Jarvis commits the changes. These are prompt rules, not enforced.
- Jarvis writes its log only to `workspaces/<id>/journal/<date>.md`, edits shared files by re-reading them and using small `Edit` changes (never a whole-file `Write`), and hands agents section pointers (path and heading), not all notes. Agents keep long text out of `CLAUDE.md`, `README.md` and `access.md` (it goes to the journal or a file under the notes folder).
- Jarvis follows the `claude-md-improver` skill when it writes `<notes>/CLAUDE.md`, and keeps Jarvis's own mechanics (journal files, commits, edit rules) out of it, so the file stays useful for a plain Claude Code session. At the end of a goal it applies `/revise-claude-md`-style learnings itself, without the approval step (git history is the safety net), under a size rule: add a line only if it is durable, project-wide and prevents a repeated mistake; merge into or replace an existing line first; send one-off incident, run or PR details to `decisions.md` or the journal; shorten the file before adding when it is over about 40 lines or 6 KB (the same merge-first rule applies to `README.md` and `decisions.md`). The prompt gives the notes path explicitly because the plugin's `find .` would search the arbiter's empty cwd. The plugin comes from the global `JARVIS_PLUGINS` default (`PLUGINS` is one constant shared by all sessions).
- `arbiterNotesPrompt()` adds these rules: when you say an item is done, Jarvis removes it from `open-items.md` and writes one dated line in the workspace journal in the same turn. It never lists a `[~]` item in an "Anything left?" answer unless the goal cannot continue without it or you ask, and does not re-check one unless it lists it. After a reset it treats every `[ ]` item as not verified and verifies it before it reports or acts. It does not re-check a verified fact that cannot change (a sha is in `origin/main`), and re-checks one that can (push state, worktrees).
- Jarvis sets the commit message of its turn with the `notes_message` MCP tool (see [Commits](#commits)).

## Open items

`workspaces/<id>/open-items.md` is one line per item:

- `- [ ] 25-11-2026 text` open.
- `- [~] 25-11-2026 text (waiting on user)` or `(not verified)` parked (the reason is a trailing parenthesis).
- `- [x] text verified 25-11-2026: what, by which check` done.
- A `(you)` right after the date, as in `- [ ] 25-11-2026 (you) Decide the name`, marks what only you can do or decide.

One parser, `parseOpenItems()` in `src/notes-layout.ts`, reads it. It also accepts `YYYY-MM-DD` dates and `[X]`, ignores prose and closed HTML comments (a comment hides lines only if it closes within 8 lines and holds no `- [` line at column 0, so a stray `<!--` hides nothing), and returns every other line that starts with `- [` (also indented) or carries an impossible date as `invalid`, never dropped. `OPEN_ITEMS_FORMAT` holds the format sentence for prompts.

**The panel.** With a notes folder, the **Open items** panel above Jarvis's chat shows the file. The header reads `N open · M for you`; the panel is gone while the file has no items.

- Open and parked items count as open. Items with `(you)` come first and carry a **you** badge; parked ones show their reason dimmed; done items are struck through.
- It is read-only. Tell Jarvis in chat that an item is done; it removes the item from the file and the panel follows within a second. Edit the file by hand and the panel follows too. The server never writes `open-items.md`.
- Lines that do not parse stay byte-identical in the file and are not shown (they are counted in `panel_status.detail.invalid`).
- The panel data is `{items: [{key, text, date, you, kind: open|parked|done, reason?, check?}]}`, kind `checklist`, title `Open items`, no badge. The key is a 16-hex hash of the normalized line. Caps (`MAX_ITEMS` 200 items, `MAX_TEXT` 200 characters, control and format characters stripped) come from `buildData()`.
- The file is the single source of truth, with no mirror. `src/openitems.ts` reads it at startup, on `fs.watch` of the folder (300 ms debounce) and at each `GET /panels`; no item removes the panel and an item brings it back; `setPanel` runs once per real change. The watcher starts in `refresh()` when it is unset and the folder exists (the folder may appear after startup), and a watcher error restarts it. `syncOpenItems()` also runs after `restoreArchivedNotes()` and in `ensureOwnNotes()`.
- Prompt gating: `agentOptions()` appends `openItemsPrompt(notes)` to the arbiter prompt only. `OPEN_ITEMS_RULES` (the file feeds the panel, re-read before each edit, you mark an item done by saying so in chat, `[x]` only after verification) needs the switch on and a notes folder.
- Turn it off with `JARVIS_OPEN_ITEMS=0`: no source, no watcher, no prompt text.

## Commits

Jarvis commits the notes folder after each arbiter turn (a sub-agent finishing triggers one through its report). Each workspace commits only the files its own agents changed (Jarvis and helpers); your own edits there stay uncommitted, except the workspace's own folder and legacy journal.

- The subject is the line Jarvis set with `notes_message` (imperative, first line only, at most 100 characters; a later call in the turn replaces an earlier one; stored per workspace and cleared after each `commitNotes()` run that reaches the commit step, whether or not it committed). Without one, a fallback built from the files: `Update a.md and journal`, `Update N notes files` above three names (journal files count as `journal`, files under `workspaces/` as `workspace notes`).
- The body is the trailer `Workspace: <name>` after a blank line (no date, git records it).
- `commitNotes()` lists the attributed paths plus its own legacy journal glob and everything under `workspaces/<id>/` and `workspaces/_archive/<id>/` (`:(glob)` pathspecs) with `git status --porcelain -z --no-renames --untracked-files=all`, file by file (so an untracked folder holding another workspace's files is never added whole), then runs `git add -A` and a pathspec commit on exactly those files. Other workspaces' changes and other staged files in a shared repo are not committed. With nothing attributed there is no commit.
- It uses the synchronous `execFileSync`, so commits of all workspaces in this one process never overlap (no locks), supplies a `Jarvis` identity when git has none, and never throws: a failure logs a warning and the files go in the next commit.
- Embedded repos under the folder are excluded (`:(exclude)` pathspecs from `embeddedRepos()`, a hand walk that does not follow symlinks): git checks an embedded repo by running `git status` inside it with that repo's own config.

## Sharing one folder between workspaces

**Git safety.** Agents can write anything under the notes folder, `.git` included, so the server's own git never takes hooks or config from inside it (hooks, `core.fsmonitor`, filter drivers, `gpg.program` and `include.path` there would run in the server process, past the permission classifier). `notesGit()` picks the repo: Jarvis's own git dir `$DATA/notes-git/<sha256 of the path, 16 hex>` if it exists, else an enclosing repo looked up from the folder's parent (so a planted `<notes>/.git` is never used; an existing repo, possibly the project's, is used as is, with its hooks), else none. Every call passes `--git-dir` and `--work-tree` explicitly. `prepareNotes()` runs `git init --separate-git-dir <Jarvis git dir>` when no repo applies, which leaves only a `.git` file in the folder for your own git. A folder whose own `<notes>/.git` exists without a Jarvis git dir (made a repo by you, or by the first version of this feature) is not committed; `commitNotes()` logs a warning with the `git init --separate-git-dir` command that moves the history out.

**Attribution.** The map `notesOwner` (absolute path to workspace id of the last writer) is filled by `pump()` through `notesToolUse()`:

- from the `Write`/`Edit`/`NotebookEdit` calls of any agent in the workspace (`notesWritten()`);
- for each `Bash` call by `notesBash()` (always for the arbiter; for a sub-agent when its `command` contains the notes path), with an mtime and size snapshot of the folder when the call starts, diffed when its `tool_result` arrives (or at `result`), so a `mv` or `rm` is attributed and a move lands in one commit as a rename;
- a sub-agent turn is also snapshotted as a whole (at the turn's first assistant message, diffed at `result`), so notes written by a script, a path read from a file or `cd "$VAR"` are claimed too. A file another workspace claimed during the turn is skipped; one nobody claimed that changed meanwhile (your edit, another workspace's still unclaimed Bash write) is claimed too. A file another workspace named in a `Write`/`Edit` during a Bash call stays with that workspace.
- A journal belongs to the workspace its key names (`journalOwner()`: the key is a workspace id, or ends in the `-xxxx` suffix of one). A name of any other shape, such as a hand-made `journal/<date>-summary.md`, belongs to nobody and is not moved; a hand-made file whose name ends in the `-xxxx` of a live workspace is taken as its journal. The journal of an archived workspace has no owner until it is restored, so a claim falls back to the writer.

Entries are dropped after a successful commit. The map is persisted to `notes-owner.json` in the data dir (temp file and rename, written when claims change and after `commitNotes()`, read at startup), so files left dirty across a restart are still committed by their workspace.

## Archive and restore

- Archiving moves `workspaces/<id>/` to `workspaces/_archive/<id>/` (`archiveNotes()`, at the end of `archiveWorkspace()`; created if missing; a symlinked `workspaces/` or `_archive` is refused; a missing source does nothing) and commits the move (the index is regenerated first, and `commitNotes()` covers `workspaces/<id>/**` and `workspaces/_archive/<id>/**`, so the move is committed with the deletions of the old path). The index skips `_archive` because its `^[a-z0-9-]+$` name check rejects `_`. The move never fails the archive.
- Open and parked items are counted first. They are not shown in the Open items panel any more and are not handed to other workspaces. The confirmation dialog says how many stay in `_archive/<id>/open-items.md` (`POST /workspaces/archive/preview {ws}` gives `{open, parked}`). A toast appears only when the folder could not be moved (`collision` or `error`); a clean archive shows none.
- An existing target is never overwritten: both folders stay, a warning is logged and the archive result says `collision`.
- Workspaces archived by an older version are moved once per start by `migrateArchivedNotes()` in `loadWorkspaces()`: for every archived workspace (`meta.json` present, id not active) whose `workspaces/<id>/` still exists in its notes folder; idempotent, active workspaces are never touched.
- Restoring (`restoreArchivedNotes()`) moves the folder back to `workspaces/<id>/` and brings the items back. An existing `workspaces/<id>/` is never overwritten (both stay, a warning is logged). The index is regenerated and the move committed.

## Context reset

Jarvis's own context is reset automatically past a limit, or with RESET (limits in [USAGE.md](USAGE.md#costs), `JARVIS_RESET_*`). With a notes folder, the server first asks Jarvis to save: it pushes a save-notes request (`[context Nk tokens, over the reset limit] ... Update <notes>/workspaces/<id>/status.md, .../open-items.md and your journal ...` plus the open-items format sentence) and resets after that turn's result and another quiet second; `JARVIS_RESET_SAVE_TIMEOUT_MS` bounds the wait. Without notes it resets at once, and the RESET confirmation warns that only a short summary survives. The seed of the new session names `open-items.md`, carries up to 20 open item texts, and tells the session to keep `[ ]` items as not verified and check them before claiming their state. The mechanics are in [ARCHITECTURE.md](ARCHITECTURE.md#runtime-model).

## Configuration

| Variable | Default | What it does |
|----------|---------|--------------|
| `JARVIS_OPEN_ITEMS` | `1` | `0` turns off the Open items panel and its prompt text (no source, no watcher) |
| `JARVIS_RESET_SAVE_TIMEOUT_MS` | `120000` | Longest the RESET button waits for the save-notes turn before it resets anyway |

The notes folder itself has no variable; it is chosen per workspace. Server data for it lives in the data dir: `notes-git/` (Jarvis's git dirs), `notes-owner.json` (claims) and `recent.json` (recent folders).

## Server endpoints

| Endpoint | Body | Answer |
|----------|------|--------|
| `POST /workspaces` | `{name, project?, notes?, ...}` | new workspace meta; a missing `notes` folder is created |
| `POST /workspaces/notes` | `{ws, notes?}` | 204; sets the notes folder (created if missing); empty clears it |
| `GET /recent[?project=path]` | | `{project: [path], notes: [path], projectNotes: {project: notes}, projectNote?: notes}`, see [Setting it up](#setting-it-up) |
| `GET /workspaces` | | each workspace carries `notes?` |
| `GET /panels?ws=<id>` | | the workspace's panels; re-reads `open-items.md` first (the watcher may lag); 404 for an unknown workspace |
| `POST /workspaces/archive` | `{ws, commit?}` | `{kept, notes: {result: moved\|collision\|none\|error, open, parked, error?}}`, 409 if dirty |
| `POST /workspaces/archive/preview` | `{ws}` | `{open, parked}`: items that stay in the archived notes folder |

## Known limits

- **Invariants** (see [ARCHITECTURE.md](ARCHITECTURE.md#invariants-you-must-keep)): the server never runs git on config agents can write; the templates in `workspaces/<id>/` are create-only for the server, and `workspaces/index.md` is replaced whole by a rename from a random-named, `O_EXCL` temp file, so a hard link or symlink an agent planted is never written through. The exceptions are `index.md` and the legacy `journal/` sync.
- Two arbiters sharing one folder can still make conflicting meaning-level edits to a shared file. Git history makes that recoverable; a merge step would prevent it.
- Commit attribution is per file: when two workspaces edit one file before either commits, both edits go in the last writer's commit, and two Bash calls in different workspaces that change notes at the same moment can claim each other's files. Changes from a `run_in_background` Bash call are not attributed, and a sub-agent turn claims any unclaimed notes file that changed during it, your edits included.
- Agents' notes rules are only prompt rules.
- A change of the notes folder applies at the next session start, not live.
